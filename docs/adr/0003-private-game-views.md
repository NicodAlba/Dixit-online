# ADR-0003 — Vistas de juego por actor y orden anónimo estable

- Fecha: 2026-10-23. Estado: aceptado; implementación U5, DEV-023. El propietario aprobó invalidaciones + REST por actor en U1–U5 y expresamente una semilla privada persistida por turno.
- Contexto: autenticar el topic no separa secretos entre participantes. Compartir Game/Turn completos revela manos, respuesta, autoría y votos antes del cierre. React dependía de esos grafos compartidos; cambiar solo la presentación no protege la transmisión.
- Decisión: las rutas existentes de juego, turno y jugador devuelven proyecciones explícitas. Participantes reciben su mano, tamaños públicos y flags propios; espectadores elegibles conservan la perspectiva intercambiable aprobada, validada contra la partida. ADMIN sin pertenencia recibe solo catálogos administrativos sin cartas. Respuesta y votos se revelan al cerrar el turno; el narrador y su perspectiva autorizada conocen antes su propia respuesta. No se modifican las entidades para ocultarlas.
- Eventos: mantener destinos y JWT existentes, transportar solo tipo/gameId/turnId y volver a consultar una única instantánea REST autorizada. El envío de acciones ocurre después del commit. El canal saliente rechaza cuerpos con campos adicionales. Una invalidación inicial dirigida a la suscripción instalada cierra la ventana entre GET y SUBSCRIBE; no transporta un estado privado ni se publica a todos como confirmación.
- Consistencia: GameViews proyecta una instantánea bajo el bloqueo de partida existente, en transacción independiente después del comando, sin reutilizar entidades antiguas de OSIV. Las respuestas tardías del frontend no sustituyen lecturas posteriores. Conectar/reconectar recupera mediante GET, sin reenviar acciones.
- Orden: nueva columna técnica nullable turns.table_order_seed, aleatoria por Turn y excluida de REST/eventos. HMAC de esa semilla e ID de Card ordena una copia de la mesa de forma estable entre actores/recargas sin revelar orden de entrada. No utiliza la clave JWT, altera listas persistidas ni identifica la respuesta. Turnos activos heredados sin semilla la obtienen bajo bloqueo; los ya terminados no se reescriben.
- Alternativas descartadas: difundir el grafo y ocultarlo con CSS; serializar un Game distinto por destinatario en un topic común; borrar asociaciones históricas; barajar en cada GET (orden inestable); ordenar por ID o mezclar semilla pública (permite inferir la primera carta). Destinos privados nuevos y broker externo no son necesarios.
- Compatibilidad: cambio deliberado y coordinado de payloads aprobado en la fase. Se conservan rutas, IDs de apariciones, acciones, puntuaciones y política de reposición ADR-0001. Frontend usa handSize/isOwn/hasPlayed/hasVoted, no necesita manos/propietarios rivales para mostrar reversos o permitir votar. Se conserva la lista de espectadores calculada al inicio también al finalizar, para que puedan recuperar el resultado; su descubrimiento social sigue limitado a partidas activas.
- Datos: no hay modificación de cartas, votos, autoría, imágenes ni historia para filtrar vistas. El esquema de desarrollo create-drop incorpora la columna al arrancar; una base persistente futura necesitará un despliegue/migración planificados, fuera de esta intervención. No se afirma que el proyecto esté preparado para producción.
- Evidencia, verificaciones y pendientes: DEV-023. Recorrido fix/game-phase-privacy → PR → develop; main corresponde exclusivamente al propietario.
